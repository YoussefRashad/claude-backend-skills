# ADR-003: Ship real source files, not descriptions of them

## Status

Accepted.

## Context

A standard can express a rule two ways: describe the correct implementation in prose, or
ship the implementation. Prose is cheaper to write and reads well in a document.

The rules most worth enforcing — exact money arithmetic, ownership-checked lock release,
verify-before-act on webhooks, a sort allowlist — are also the ones hardest to restate
correctly from memory, and the most expensive to get wrong late.

## Decision

Ship 16 real, compiling TypeScript files under `backend-standards/templates/src/`, copied
into the target project. Each enforces one rule that is easy to get wrong and expensive to
get wrong late. Specs ship with the files they test.

`SKILL.md` step 6 copies **only** what the service actually uses: "an unused template is
dead code, and dead code teaches the next person that the standard is decorative."

## Alternatives Considered

| Option                         | Pros                                                                         | Cons                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Describe in prose only         | Shorter documents; nothing to maintain                                       | A description of `AbstractEntity` drifts from the real one; every project re-derives the money rules by hand |
| Ship source templates (chosen) | The rule and its implementation cannot disagree; specs make claims checkable | Templates must compile and lint under the canonical config, and must be re-validated per framework major     |
| Publish as an npm library      | Real versioning; one implementation                                          | Needs registry infrastructure; a project cannot adapt a file it does not own                                 |

## Consequences

- **A template defect ships everywhere**, silently, until someone notices — which is why
  `templates/src/` requires code-owner review and why the files carry unusually heavy
  explanatory comments.
- The templates must stay prettier-clean and lint-clean against the canonical config, or
  every new project starts with a failing gate.
- Claims about them must state scope: verified against Nest 11, and **not** supported on
  Nest 12, whose CLI generates oxlint, Vitest and `nodenext`.
- Specs are the mechanism that turns a claim into something checkable — `money.util.spec`
  proves the exactness claim, `sortable.spec` proves the allowlist rejects prototype keys.

## Evidence

- `README.md` § "Why source templates rather than descriptions" — "A description of
  `AbstractEntity` drifts from the real `AbstractEntity`. A file does not."
- The per-file table in `README.md` and `backend-standards/README.md` mapping each
  template to the defect it prevents.
- `backend-standards/SKILL.md` step 6, including "Copy the money spec **with** the money
  util. It is what makes the exactness claim in `01` §6 checkable rather than asserted."
