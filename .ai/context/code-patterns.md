# Authoring patterns

How the three kinds of file in this repo are written. Inferred from reading the existing
ones — match them rather than inventing a fourth style.

## 1. A `SKILL.md`

YAML frontmatter with `name` and `description`, then prose.

- **`description` is a trigger list, not a summary.** It enumerates the phrasings that
  should invoke the skill ("create a new service for X", "unify the eslint config"),
  because that string is what the model matches against. Both existing descriptions run
  650–850 characters; keep new ones in that range.
- Numbered procedure steps, each with the _reason_ the step exists in that order — e.g.
  `git init` before `npm install` because Husky's `prepare` needs `.git`.
- Decisions are quoted blocks signed with a name and date, and say **what was actually
  verified** versus what was assumed.
- Footgun boxes use `## ⚠️ Critical <thing> footgun` and follow the same shape: what the
  setting is, what breaks, why it is invisible, what not to do about it.

## 2. A reference document (`references/NN-*.md`)

- Opens with a blockquote stating scope and precedence.
- Numbered `##` sections, referenced elsewhere as `01` §6.
- **Every rule carries an RFC 2119 keyword, or it is explicitly explanation.**
- A rule states the failure it prevents, concretely. Not "use a timeout" but "a client
  without one waits forever, holding a request slot and a connection".
- Code blocks are labelled `// MUST` / `// MUST NOT` and show both sides.
- **Portability rule:** `01` and `02` name no concrete class, package or file. Anything
  that does belongs in `03-project-architecture.md`. This is why the correlation-ID and
  rate-limit templates are wired from `SKILL.md` step 6 rather than named in `01` §14.

## 3. A source template (`templates/src/**/*.ts`)

These are the highest-signal files in the repo and have the strictest conventions.

- **Real, compiling TypeScript.** Never pseudocode, never an ellipsis. See `ADR-003`.
- A file-level block comment that states, in order:
  1. what the file is,
  2. `Standard: .ai/standards/NN-….md §N`,
  3. **the mistake it prevents**, in prose, with the mechanism.
- The comment explains _why_, not _what_. Compare: "TWO THINGS THIS GETS RIGHT THAT A
  NAIVE LOCK DOES NOT" — then the two, with the failure each avoids.
- Where a rule is subtle, the comment names the wrong version explicitly so a reader
  recognises it: a bare `DEL` deletes someone else's lock; `map[key]` walks the prototype
  chain; `response.statusCode` is read before Nest sets it.
- An `eslint-disable-next-line` **always** carries a `--` justification.
- Imports follow the canonical `simple-import-sort` groups: `node:` → external → `@/` →
  parent → sibling. Within the sibling group, **nested paths sort before flat ones**
  (`./common/x` before `./app.module`) — it is regex-index order, not alphabetical.
- **Value imports for anything injected.** `import type` on a constructor parameter type
  erases the decorator metadata and breaks DI. See the footgun box in
  `toolchain-config/SKILL.md`.

## 4. A spec (`*.spec.ts`)

A spec ships beside the file it tests, and exists to make a claim in the standard
_checkable_ rather than asserted. Each opens with a comment saying which claim.

- Names follow `should <expected> when <condition>`.
- The first test is usually the regression the obvious implementation gets wrong —
  `POST` returning `statusCode: 200`, `sortBy=toString` passing the allowlist.
- Assertions are exact values, not snapshots.

## 5. Markdown conventions (all files)

- Prettier-formatted, 100 columns, `proseWrap: preserve`. `npm run check` enforces it.
- Tables for anything comparative; em-dashes for asides.
- Bold is for the operative word in a rule, not for emphasis generally.
- A claim about verification states its scope and date. "Validated" without a scope is
  the failure mode this repo keeps correcting.
