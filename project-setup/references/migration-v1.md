# Migrating from project-setup v1

v1 was Claude-only: a router `CLAUDE.md` with `@imports`, `.ai/context`, `.ai/decisions`, `docs/`,
`.claude/agents/{reviewer,docs-sync}.md`, `.claude/settings.json`, sometimes `.claudeignore`, and a
`<!-- Generated by project-setup · Source commit: … -->` provenance comment.

## Preconditions

- Prefer a dedicated branch (suggest `chore/ai-setup-v2`; do not create it yourself).
- A clean tree is **not** required. `prepare` flags targets with uncommitted user changes; those are shown to the
  user explicitly, and the draft must be built from the current (dirty) content. Never stash or reset.
- Only one active `project-setup` per tool (see `references/claude.md` "Retiring v1").

## Steps

1. **Inventory** v1 artifacts (detect output + reads). Note which `.ai/context` and `docs/` files exist; they are
   living docs and become `merged` ownership. Do not regenerate them unless the user asks; v2 only fills gaps.
2. **Split `CLAUDE.md`** section by section:
   - tool-neutral rules (security, coding, DB, commands) → `AGENTS.md` managed blocks;
   - Claude-only content → stays in `CLAUDE.md` below `@AGENTS.md`;
   - user-authored text that is neither → stays where it is, untouched.
   Show the mapping table (section → destination) in the Phase 0 plan.
3. **Convert eager imports.** v1 loaded every context file at startup via `@.ai/context/...`. In `AGENTS.md`
   these become backticked paths in the navigation table (read on demand by both tools). In `CLAUDE.md`, keep an
   `@import` only if the user wants that file in every Claude session (usually none, at most
   `critical-modules.md`). Imports do not reduce context cost.
4. **Agents.** Move the bodies of `.claude/agents/reviewer.md` and `docs-sync.md` to `.ai/agents/` (as the v2
   canonical definitions, merging any project-specific additions the user made), and replace the Claude files
   with the v2 wrappers **at the same paths and names**, because `pr-review` and `audit` launch
   `.claude/agents/reviewer.md`. Verify by grepping those skills before changing any name.
5. **Settings.** Run `merge-claude-settings.mjs`. Expect the report to list:
   - `Bash(DROP DATABASE *)`-style entries as ineffective (keep unless the user removes them);
   - the v1 `PostToolUse` hook as malformed (legacy shape never ran). Ask: remove, or convert to the current
     shape. Recommend lint enforcement via husky/lint-staged instead (tool-agnostic), not an agent hook.
6. **`.claudeignore`** has no effect in Claude Code. Confirm its entries are covered by Read denies, then
   propose deleting it (user decision; it is outside the write allowlist, so the user deletes it).
7. **Approvals for files the skill does not own.** v1 files have no managed blocks and no manifest entry, so any
   change other than adding new blocks (the `@AGENTS.md` line, converting the eager import, replacing the v1
   reviewer with the wrapper) is rejected by prepare until the user approves it:
   `prepare … --approve-user-content CLAUDE.md,.claude/agents/reviewer.md`. Expected and correct.
8. **Provenance.** Leave v1 comments in living docs; they are history. New v2 files carry no timestamps.
9. Prepare → diff review → commit → validate → runtime verification, as in `SKILL.md`.

## What must still work afterwards

- `pr-review` launches the reviewer and gets v2 behaviour.
- Claude loads `AGENTS.md` through the import (check with `/context` or `/memory`).
- Codex loads `AGENTS.md` and lists `reviewer`/`docs_sync` custom agents.
- `validate.mjs` reports no failures.
